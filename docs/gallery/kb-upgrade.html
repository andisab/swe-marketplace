PostgreSQL 14 to 16 upgrade runbook

PostgreSQLOperationsVolatile: re-check before each window

This runbook takes one production cluster from PostgreSQL 14.12 to 16.4 with pg_upgrade --link in a 20-minute window. It was last run on db-prod-eu-2 on 2026-10-09 (18 minutes, no rollback). Pair it with Rollback, which you must have read before step 4.

Fleet state before you start

Every cluster on the list below must be on 14.12 or later, because pg_upgrade from 14.11 hits the pg_stat_statements catalog bug. The last column is the extension that blocks the upgrade until its new version is installed.

Trap --link mode makes the old cluster unusable the moment the new one starts. The rollback plan is a replica promotion, not a downgrade. Confirm the async replica is within 5 seconds of lag before step 4 or you will roll back to stale data.

The window, minute by minute

Eighteen minutes on a 640 GB cluster; budget 25 for 2 TB. The sequence diagram shows who talks to whom; the table under it is the checklist you tick.

  participant P as Primary v14

  O->>A: enable maintenance mode, t+0
  O->>P: CHECKPOINT and stop, t+2
  O->>N: pg_upgrade check, t+3
  N-->>O: clusters compatible
  O->>N: pg_upgrade in link mode, t+5
  O->>N: start and ANALYZE IN STAGES, t+11
  O->>R: pg_basebackup from N, t+12, background
  O->>A: disable maintenance mode, t+14
  A->>N: traffic

Field tip Run step 1 the day before, on the replica, with the new binaries installed. Every blocked upgrade in the last year failed on an extension version, never on the data.

What changed in query latency after the upgrade

p95 per service on db-prod-eu-2, the week before and the week after, in milliseconds. The planner changes in 16 helped every service; the cache that went in the same week explains checkout.

Scenario drills

Scenario drill

Exercises: Rollback decision. At t+9 pg_upgrade stops with an error about pg_largeobject. The window has 11 minutes left.

How a strong operator answers

Promote the async replica now (4 minutes), point the app at it, and take the cluster off the upgrade list. Debugging pg_upgrade inside the window is how a 20-minute outage becomes a 2-hour one.
